# ADR-005 — Merge-Blocking Evaluation Gate in CI

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

A prompt edit, a threshold change, or a model swap can regress answer quality
without breaking a single test.  The unit suite covers the request path, the
resilience patterns, and the wiring; none of it can tell whether the answers got
worse, because correctness here is a judgement about grounding, not an assertion
about a return value.

The evaluation harness existed before this decision and could be run locally.
That is the part that does not work: a local run is a thing a developer chooses
to do, and a regression ships when someone is in a hurry.  An evaluation that
does not gate anything is a report, and reports about quality get read after the
incident rather than before the merge.

## Decision

Run the evaluation suite in CI on every push and pull request to `main`, and fail
the build when the aggregate scores fall below a floor.

`.github/workflows/ci.yml` runs two jobs.  `lint` byte-compiles the pipeline,
judge, and eval modules.  `eval-gate` runs `needs: lint`, then executes
`evals.run_eval` to produce `evals/reports/latest.json`, then `evals.gate` to
check it.

`evals/gate.py` reads the report's aggregates and enforces two floors:

| Metric | Floor |
|---|---|
| `mean_relevancy` | 0.6 |
| `mean_correctness` | 0.5 |

Either one below its floor prints the failing value against the floor and exits
non-zero, which fails the job.  A missing or malformed report also exits
non-zero, so a harness that did not run cannot be mistaken for a harness that
passed.

The gate depends on live provider keys, and **a missing key fails the build
rather than skipping the gate**.  The `Verify secrets` step checks
`DEEPSEEK_API_KEY` and `OPENAI_API_KEY` before the harness runs and exits 1 if
either is absent.  This is the decision that makes the rest of it real: a gate
that silently no-ops when unconfigured is worse than no gate, because it reports
green.

The report is uploaded as an artifact with `if: always()`, so a failing run
leaves behind the evidence of what scored low.

## Alternatives Considered

- **Report-only dashboards** — a quality trend published somewhere visible, with
  no enforcement.  Discarded: it relies on somebody looking at the right moment,
  and the moment that matters is the one before a merge.
- **Manual review of eval output before merge** — a human reads the scores and
  decides.  Discarded: it does not scale, and it fails in exactly the conditions
  that produce regressions, which are haste and confidence.
- **Blocking on per-case pass rather than aggregate means** — stricter, and it
  catches a single badly regressed question that a mean would absorb.  Discarded
  for now: with a 12-case golden set and a model-graded metric, per-case
  thresholds would fail the build on judge variance, and a gate that cries wolf
  gets disabled.
- **Running the gate only on release** — cheaper, since it would run far less
  often.  Discarded: the point is to prevent the bad commit from reaching `main`,
  and a release-time check finds it after several changes have already landed on
  top of it.

## Consequences

- **Positive:** a quality regression below the floors cannot merge to `main`.
- **Positive:** the failure names the metric and the value, and the report
  artifact is retained, so diagnosis starts with data rather than a re-run.
- **Negative:** CI now spends real money and real time on every push, because the
  gate makes live provider calls.  The suite's duration was not measured for this
  record.
- **Negative:** CI depends on external provider availability.  A provider outage
  fails the build for reasons unrelated to the change being tested, and the
  `Verify secrets` step means a fork without secrets cannot run the gate at all.
- **Negative:** the floors are absolute, not relative to the previous run.  A
  change that degrades scores from well above the floor to just above it passes
  silently.  This catches regressions past a line, not regressions as such.
- **Note:** the gate does not block the Docker workflow.  `docker.yml` is a
  separate workflow triggered on the same events, with no `needs` relationship to
  `eval-gate`; it builds the image with `push: false` and smoke-tests `/health`.
  Nothing is published from CI, so there is no publish for the gate to block.
  Making the image build depend on the gate would require wiring the two
  workflows together, which has not been done.
