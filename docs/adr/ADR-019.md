# ADR-019: Shadow Evaluation and Fail-Closed Promotion Gate

**Status:** Accepted  
**Date:** 2026-09-24  
**Deciders:** Engineering team

---

## Context

Changing the RAG pipeline configuration — model, retrieval strategy, top-k, prompt template — carries silent quality risk. A configuration that looks faster or cheaper may degrade faithfulness or answer relevancy. Without a structured comparison mechanism, regressions are discovered only after they affect production traffic.

We need a way to:
1. Run a candidate configuration on representative queries alongside the current baseline.
2. Aggregate metric scores from both runs.
3. Make a promotion decision that is conservative by default (fail-closed).

---

## Decision

We introduce `src/rag/promotion_gate.py` implementing a shadow evaluation + promotion gate:

- **`ShadowResult`** — accumulates per-metric scores from N shadow queries, computing means with count-aware averaging.
- **`compare(baseline, candidate, primary_metrics, margin)`** — compares aggregate means. Fail-closed in three cases: insufficient samples, absent primary metric in either run, or candidate mean < baseline mean + margin on any primary metric.
- **`run_shadow_experiment(queries, baseline_fn, candidate_fn)`** — runs all queries through both callables, tolerates exceptions (failed samples are skipped), returns a `PromotionDecision`.
- **`PromotionDecision`** — immutable dataclass with `promote: bool`, `reason`, per-metric `checks`, and summaries.

### Thresholds

| Constant | Value | Rationale |
|---|---|---|
| `MIN_SHADOW_SAMPLES` | 5 | Below 5 samples the mean is statistically unreliable; fail-closed. |
| `PROMOTION_MARGIN` | 0.02 | Candidate must be at least 2% better on each primary metric. Guards against noise-level differences being accepted as improvements. |
| `PRIMARY_METRICS` | `("faithfulness", "answer_relevancy")` | These are the two metrics most predictive of user-perceived quality in our eval harness (ADR-017). |

### Failure modes and gates

| Condition | Outcome |
|---|---|
| Either side has < MIN_SHADOW_SAMPLES | `promote=False` — insufficient data |
| Primary metric absent from either run | `promote=False` — metric absent, not zero |
| Candidate mean < baseline mean + margin | `promote=False` — failed margin check |
| Exception in baseline or candidate call | Sample skipped; total sample count decremented |
| All primary metrics pass margin check | `promote=True` |

---

## Alternatives Considered

1. **A/B test on live traffic** — distributes quality risk to real users. Rejected: we want the gate before any traffic exposure.
2. **Single-run comparison without margin** — equal scores would accept a candidate. Rejected: noise in eval scores can make equal-quality configurations appear better. The margin guards against this.
3. **Fail-open (default promote=True when data is missing)** — simpler, but contradicts the principle in ADR-015 that uncertainty should block promotion, not allow it.

---

## Consequences

- Positive: promotion decisions are repeatable, logged, and auditable (`PromotionDecision.checks` captures per-metric detail).
- Positive: no real LLM calls in unit tests — both callables are injectable, keeping the test suite fast.
- Negative: requires N ≥ 5 representative queries with ground-truth metrics to produce a decision. Building and maintaining that query set is operational overhead.
- Neutral: the gate is currently invoked manually; it is not yet wired into a CI step or a deployment pipeline. That integration is a follow-up item.
