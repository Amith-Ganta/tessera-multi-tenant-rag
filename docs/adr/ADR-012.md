# ADR-012: LLM Deployment Governance

**Status:** Accepted
**Date:** 2026-09-20
**Deciders:** Amith Ganta

## Context

Tessera's `MODEL_REGISTRY` (in `src/rag/models.py`) registers four models across
two providers: `deepseek-flash`, `deepseek-chat`, `gpt-4o-mini`, `gpt-4o`. The
LiteLLM fallback chain (`src/rag/llm.py`) independently defines which model handles
overflow. The canary router (ADR-011) adds a third routing dimension. A judge-specific
model runs inside the worker pool. Without a governance document, operators have no
single place that records:

- which model is the approved default and why
- what criteria trigger a model upgrade or rollback
- how cost and quality constraints are balanced across routing dimensions
- what the policy is when a new model is added or a provider is deprecated

This creates four deployment models that are independently configured but share no
common promotion criteria or rollback procedure.

## Decision

We define four LLM deployment models and one routing pattern as the authoritative
policy for this system.

### Deployment Model 1 — Default (primary request path)

**Model:** `deepseek-flash` (`deepseek/deepseek-flash` via LiteLLM)  
**Selection criterion:** Lowest cost ($0.07/1M tokens) with acceptable quality on the
eval gate (mean relevancy >= 0.6, mean correctness >= 0.5).  
**Override:** `CHAT_MODEL` env var. Any override must be present in `MODEL_REGISTRY`;
unknown values fall back to `deepseek-flash`.

### Deployment Model 2 — Canary (phased rollout)

**Model:** `MODEL_CANARY_VERSION` env var (default: `gpt-4o-2024-11-20`)  
**Traffic share:** `MODEL_CANARY_PERCENT` percent of tenants (deterministic SHA-256
hash per tenant_id).  
**Promotion criteria:** canary model must match or exceed the default on faithfulness
and answer relevancy over >= 1,000 live requests (see ADR-011).  
**Rollback:** set `MODEL_CANARY_PERCENT=0` — no redeploy needed; config reload only.

### Deployment Model 3 — Fallback (provider failure)

**Chain:** `deepseek/deepseek-flash` → `openai/gpt-4o-mini`  
**Trigger:** LiteLLM `litellm.exceptions.APIError` or `RateLimitError` from the
primary provider.  
**Circuit breaker:** 5 consecutive failures open the breaker (30 s recovery). The
fallback chain is attempted once per opened breaker before the 503 fires.  
**Policy:** fallback to `gpt-4o-mini` is automatic and transparent; no operator
action required. If both providers are down simultaneously, the system returns HTTP
503 with `Retry-After: 30`.

### Deployment Model 4 — Judge (background evaluation)

**Model:** `gpt-4o-mini` (hardcoded in DeepEval metric calls)  
**Isolation:** judge model runs in the worker process, never on the request path.
It is intentionally decoupled from the chat model: a canary chat model should
not also canary the judge, as that would create confounded eval signals.  
**Cost ceiling:** judge jobs consume approx. 8.5 metric calls each; at 10K req/day
with `run_eval=True`, judge cost approaches the OpenAI 500 RPM limit at 3× peak
(see `docs/capacity-model.md`). If cost exceeds budget, reduce `run_eval` sampling
rate via `EVAL_SAMPLE_RATE` env var (default: 1.0 = every request).

### Routing Policy Engine (Future)

A future policy engine would consolidate the four deployment models into a single
`ModelRouter` class: a pluggable set of rules evaluated per-request (cost budget,
canary percent, tenant tier, live eval score) producing a single `(litellm_id, context)`
tuple. This ADR records the routing rules that the policy engine would codify; it
does not implement the engine. The current approach (three independent env vars +
fallback chain) is acceptable until tenant count exceeds 100 or provider catalogue
exceeds 6 models.

## Alternatives Considered

- **Single model, no registry** — simplest. Rejected: cost and quality needs differ
  per use case (chat vs. judge vs. canary); a single model cannot serve all three
  optimally.
- **LLM gateway (LiteLLM proxy server)** — centralises all routing in a sidecar.
  Deferred: adds network hop and new infrastructure dependency. The current in-process
  LiteLLM client achieves equivalent routing with lower latency and fewer moving parts.
- **Per-tenant model selection** — tenants choose their own model from the registry.
  Deferred: creates billing complexity and makes aggregate quality guarantees difficult
  to enforce. Revisit when enterprise tier is introduced.
- **Shadow mode evaluation of canary** — run both models on every request, use canary
  result only for eval. Rejected: doubles inference cost without giving the canary
  model real user interaction patterns (see ADR-011).

## Consequences

- **Positive:** a single document describes all four routing dimensions; operators
  know where to look when a model needs to change.
- **Positive:** promotion and rollback criteria are explicit and pre-agreed; they
  cannot be overridden informally.
- **Positive:** judge model is explicitly decoupled from chat model, preventing
  confounded eval signals during a canary rollout.
- **Negative:** policy is encoded in documentation and env vars, not in code.
  Drift between this ADR and the implementation is possible if future changes do
  not update both. Mitigation: CI linting step to verify `MODEL_REGISTRY` and
  `_FALLBACK_CHAIN` remain consistent with the policy stated here.
- **Deferred:** cost-based routing (automatically select the cheapest model that
  passes quality threshold) requires the policy engine described above.
