# ADR-001 — LiteLLM Provider Abstraction over Direct Provider SDKs

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

The project calls a language model from several places: the answer generator, the
query router, the judge, and each retrieval strategy that rewrites or expands a
query.  It also needs to reach more than one provider — DeepSeek as the primary,
OpenAI as the standby — because a single provider's rate limit or transient 5xx
should not take the whole system down.

Integrating each provider's own SDK at each call site would mean writing the
failover logic once per call site and keeping those copies in agreement.  Three
concerns would be duplicated rather than shared: which provider to try next when
one fails, what a call is allowed to cost, and how a call is traced.  Those are
exactly the concerns that go wrong quietly when they are copy-pasted — one call
site gets a timeout and another does not, and the difference only surfaces during
an incident.

## Decision

Route every model call through a single `complete()` function in `src/rag/llm.py`,
built on LiteLLM.  No module calls a provider SDK directly.

That one entry point is where three things are enforced:

**Fallback.** `_FALLBACK_CHAIN` is `["deepseek/deepseek-chat", "openai/gpt-4o-mini"]`.
LiteLLM retries the same request against the standby when the primary fails, with
each fallback carrying its own API key so the provider switch is clean.  A standby
whose key is absent is dropped from the chain rather than failing the call, so a
partially configured environment degrades instead of breaking.  A per-call
`REQUEST_TIMEOUT_SECONDS` (default 30) ensures a stalled provider fails fast into
that chain instead of hanging the request.

**Cost control.** `MAX_OUTPUT_TOKENS` caps any single answer, and
`DAILY_SPEND_USD_CAP` (default 5.0 USD) refuses further calls once the estimated
process-wide spend crosses the line.  Prices in `_USD_PER_1M_TOKENS` are public
list rates used for an estimate and a guard, not billed figures, and the analytics
log records them as estimates.

**Observability.** Each call is wrapped in `trace_llm`, recording the model
actually served, token usage, and estimated cost.  With tracing unconfigured this
is a no-op and nothing else changes.

Because the model is resolved through `MODEL_REGISTRY` rather than hard-coded,
swapping a provider is a configuration change.  The canary mechanism (ADR-011)
plugs into this same point — `_select_model()` runs before resolution, so a canary
model inherits fallback, cost caps, and tracing without any additional wiring.

## Alternatives Considered

- **Direct provider SDKs at each call site** — no abstraction layer to learn, and
  full access to each provider's specific features.  Discarded: fallback, cost
  capping, and tracing would each be reimplemented per call site, and the copies
  would drift.
- **LangChain's provider layer** — the project already uses LangChain for parts of
  the retrieval path, so this would add no new dependency.  Discarded: it couples
  model access to LangChain's abstractions, which means a future move away from
  LangChain would have to rewrite every model call rather than one module.
- **A hand-rolled wrapper over the provider SDKs** — full control over the
  failover semantics.  Discarded: it is the same abstraction LiteLLM already
  provides, with the retry, timeout, and provider-quirk handling still to write
  and maintain.

## Consequences

- **Positive:** one place to change fallback order, cost policy, or tracing, and
  one place to read to find out what any model call actually does.
- **Positive:** provider swap is a config change against `MODEL_REGISTRY` rather
  than a code change at every call site.
- **Positive:** the circuit breaker and bulkhead (ADR-008) wrap this single
  function, so every model call in the project inherits both without each caller
  opting in.
- **Negative:** LiteLLM sits between the code and the provider, so a
  provider-specific feature is available only once LiteLLM exposes it, and a bug
  in the abstraction affects every call path at once.
- **Negative:** the spend guard is per-process and in-memory.  With four uvicorn
  workers the effective cap is four times the configured value, and it resets on
  restart.  It is a runaway-loop guard, not a billing control.
- **Note:** `complete_stream()` duplicates the fallback-chain construction rather
  than sharing it with `complete()`, and does not pass through the circuit breaker
  or bulkhead.  That divergence is a known inconsistency in the current code.
