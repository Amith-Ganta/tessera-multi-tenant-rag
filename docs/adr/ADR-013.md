# ADR-013: Tenant Identity Derivation from User ID

**Status:** Accepted  
**Date:** 2026-09-23  
**Replaces:** n/a  
**Replaced by:** n/a

## Context

Tessera is a multi-tenant system where each user must be isolated from other users'
documents, caches, rate-limit counters, and audit logs. A tenant identifier is needed
to key all per-user resources. Two approaches were considered:

1. Allow the caller to supply a `tenant_id` in request bodies.
2. Derive the tenant slug from the authenticated `user_id` stored in the database.

## Decision

The tenant slug is derived server-side from the numeric `user_id` as
`"user-" + str(int(user_id))`. This derivation happens in `auth.tenant_slug(user_id)`
(`src/auth/auth.py:280–282`) and is called from the `/ask` endpoint after token
validation (`src/api/app.py:456`).

User-supplied tenant IDs are never accepted.

## Rationale

Caller-supplied tenant IDs create an authorization bypass: a user could supply
another user's tenant ID and read from or write to their document store, rate-limit
counter, or cache. Deriving from the authenticated `user_id` eliminates this class of
vulnerability entirely.

The `int()` cast in `tenant_slug` prevents injection of path-traversal characters
(e.g. `../../etc/passwd`) that could escape the per-tenant corpus directory.

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| User-supplied `tenant_id` in request body | Authorization bypass risk |
| Email-based slug | Email can change; would invalidate existing data |
| UUID at registration | More robust for multi-region, but adds complexity for no present benefit |

## Trade-offs

- **Pro:** Simple, unforgeable, consistent.
- **Con:** Tenant slug changes if user rows are deleted and re-inserted (mitigated by
  never deleting users — only deactivating them).

## Consequences

All per-tenant resource keys in Redis, filesystem paths, and analytics logs use the
`user-N` format. Any migration that changes `user_id` sequences must also migrate
the associated data.

## Operational Impact

Runbook for cross-tenant data leaks (`docs/runbooks/incident-response.md`, Runbook 3)
assumes this derivation. Any change here invalidates that runbook.

## Revisit Trigger

If Tessera adds organisation-level tenancy (multiple users sharing a single resource
pool), a new tenant model is needed and this ADR must be superseded.
