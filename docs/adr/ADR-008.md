# ADR-008 — Rate Limiting, Circuit Breaker, and Bulkhead

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

Three independent failure modes needed to be addressed without introducing
shared state or new heavyweight dependencies:

1. **Rate limiting** — a single tenant could flood `/ask` and consume all
   OpenAI credits.
2. **Cascading failure** — repeated downstream timeouts (OpenAI, DeepEval)
   would back up the thread pool and degrade the API for all tenants.
3. **Resource contention** — judge calls share the same httpx connection pool
   as primary LLM calls; a spike in evaluations would starve answer generation.

## Decision

Implement three lightweight in-process / Redis-backed patterns:

- **Rate limiter** (`src/resilience/rate_limiter.py`): Redis INCR/EXPIRE
  sliding-window (fixed-window approximation), 100 req/min per tenant.
  Fails open when Redis is down.
- **Circuit breaker** (`src/resilience/circuit_breaker.py`): three-state
  (CLOSED → OPEN → HALF_OPEN) in-process breaker.  Opens after 5 consecutive
  failures; probes after 30 s.  Named breakers so the LLM and judge paths fail
  independently.
- **Bulkhead** (`src/resilience/bulkhead.py`): counting semaphore separates
  `MAIN_POOL_SIZE=10` (primary LLM calls) from `JUDGE_POOL_SIZE=3` (eval calls).

## Alternatives Considered

- **Istio / Envoy** — service-mesh rate limiting and circuit breaking at the
  network layer; no application code needed.  Deferred: the project runs without
  a mesh today.
- **Tenacity** — retry library with backoff; does not cover rate-limiting or
  bulkhead patterns.  Not sufficient.

## Consequences

- **Positive:** all three patterns are testable without a real network; each
  degrades gracefully (fail-open, fall through, or surface an immediate 503).
- **Negative:** in-process circuit-breaker state is not shared across API
  replicas — each pod tracks its own failure count.  Redis-backed shared state
  is a future improvement noted in ADR-010.
