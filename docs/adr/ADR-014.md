# ADR-014: Circuit Breaker State Scope — In-Process Only

**Status:** Accepted  
**Date:** 2026-09-21  
**Deciders:** Engineering  
**Supersedes:** None  
**Related:** `docs/DEPENDENCY_FAILURE_MATRIX.md` (MM-03), ADR-012

---

## Context

Tessera's circuit breaker (`src/resilience/circuit_breaker.py`) protects calls to
the LLM provider and the embedding API. Its current implementation keeps all state
(failure count, open/half-open timestamps) in an in-process Python object protected
by a `threading.Lock`.

In a horizontally-scaled deployment (multiple API replicas behind a load balancer),
each replica maintains its own independent breaker state. This means:

- A provider outage opens breakers **independently** as each replica accumulates
  consecutive failures. There is no shared signal to open all replicas immediately.
- A recovery after an outage allows each replica to probe independently in HALF_OPEN,
  so multiple simultaneous probe requests may hit a recovering provider.
- One replica may have opened its breaker while another is still in CLOSED state,
  leading to inconsistent behaviour across requests routed to different replicas.

This gap was identified as **MM-03** in `docs/DEPENDENCY_FAILURE_MATRIX.md`.

---

## Decision Options Considered

### Option A — Redis-backed shared circuit breaker state

Persist failure counts and state transitions to Redis. All replicas read/write
the same key. Implemented via an atomic Lua script or SETNX/INCR to maintain
consistency without distributed locks.

**Pros:**
- Consistent breaker state across all replicas.
- One replica's failures inform the others immediately.

**Cons:**
- Adds Redis as a **dependency of the circuit breaker itself** — a component that
  exists precisely to protect against dependency failures. A Redis outage would now
  impair the circuit breaker.
- Adds latency on every protected call (Redis round-trip for state read).
- Requires careful handling of Redis unavailability (fall back to in-process state?
  fail open? fail closed?), each choice with its own trade-offs.
- Increases operational and code complexity for a portfolio project at single-replica
  scale.

### Option B — Document the limitation + emit a startup log warning (chosen)

Keep state in-process. Document the scope limitation clearly in the circuit breaker
module docstring (already present), this ADR, and the dependency failure matrix.
Emit a WARNING log at application startup so operators see the limitation in every
deployment.

**Pros:**
- No new failure mode introduced — the circuit breaker remains self-contained.
- No latency added to the hot path.
- Fully honest: the limitation is visible in logs, docs, and ADR.
- Appropriate for the current deployment scale (single replica in portfolio/demo use).

**Cons:**
- Each replica still opens independently in a multi-replica scenario.
- No automatic coordinated circuit opening across replicas.

---

## Decision

**Option B** is chosen.

Rationale:

1. **No additional failure modes.** The circuit breaker's purpose is to absorb
   dependency failures. Making it depend on Redis would couple its availability to
   the very class of external service it is guarding against.

2. **Portfolio and demo scale.** Tessera is deployed as a single replica in its
   current form. The multi-replica inconsistency is a theoretical concern, not a
   live operational problem.

3. **Honest documentation over false confidence.** A startup warning and this ADR
   make the limitation visible to every operator without pretending the problem is
   solved.

4. **Upgrade path is clear.** If Tessera scales to multiple replicas, Option A can
   be implemented as a targeted enhancement. The interface (`CircuitBreaker.call()`,
   `before_call()`, `on_success()`, `on_failure()`) is stable and would not change.

---

## Consequences

- `src/api/app.py` emits a startup WARNING log referencing this ADR.
- `src/resilience/circuit_breaker.py` module docstring already documents the
  in-process scope constraint.
- `docs/DEPENDENCY_FAILURE_MATRIX.md` MM-03 entry is updated to reflect this
  accepted limitation with a pointer to this ADR.
- No code changes to the circuit breaker implementation.
- If a future operator scales to multiple replicas, they should revisit Option A
  or implement a coordinating layer (e.g., Redis Lua script, or a sidecar that
  broadcasts circuit events via pub/sub).
