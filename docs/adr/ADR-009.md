# ADR-009 — Redis Checkpointer for Stateless A2A Agents

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

The A2A orchestration layer persists agent workflow state (transcript, retry
count, last draft, tenant slug) to SQLite via `SQLiteCheckpointer`.  SQLite is
a file-local store: two replicas sharing the same `TESSERA_CHECKPOINT_DB` path
over a network file system incur file-lock contention, and pods on different
nodes cannot share state at all.  This makes the API stateful — a pod restart
or load-balancer reroute to a different replica breaks workflow resumption.

## Decision

Add a `RedisCheckpointer` (`src/state/redis_checkpointer.py`) that implements
the same three-method interface (`save_state`, `load_state`, `delete_state`) as
`SQLiteCheckpointer`, using Redis SETEX/GET/DEL with a configurable TTL
(default 24 h, via `CHECKPOINTER_TTL_SECONDS`).  The active backend is selected
by `CHECKPOINTER_BACKEND` in `config.py` ("sqlite" keeps the Phase 4 default;
"redis" enables the new path).  A factory function (`checkpointer_factory()`)
returns the correct instance at startup so no call-site changes are needed.

## Alternatives Considered

- **PostgreSQL JSONB** — durable and queryable, but adds a heavyweight dependency.
  Discarded.
- **DynamoDB/Firestore** — managed and scalable, but cloud-vendor specific.
  Deferred.
- **Keep SQLite with shared EFS mount** — possible on EKS but slow (NFS latency)
  and operationally fragile.  Discarded.

## Consequences

- **Positive:** API replicas are now stateless — any pod can resume any workflow.
  Deferred cleanup via Redis TTL eliminates the need for a separate eviction job.
- **Negative:** Redis becomes a harder dependency (SQLite fallback still works but
  is not HA in multi-replica mode).
- **Transition:** existing SQLite checkpoints are not migrated; long-running
  threads started before the cutover will fall back to a fresh workflow.
