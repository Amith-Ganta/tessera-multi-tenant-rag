# ADR-010 — Autoscaling Strategy: HPA on Queue Depth for Judge Workers

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

The capacity model (`docs/capacity-model.md`) shows that at 1M req/day with 3×
peak, 655 judge worker replicas would be needed if each runs a single-threaded
concurrency=1 loop.  Worker pods are 97% I/O-bound (all time waiting on the
OpenAI/DeepEval API).  CPU utilisation stays near zero regardless of load —
scaling on CPU would never trigger.  A custom metric (Redis queue depth) reflects
the actual backlog and scales proportionally to the work to be done.

## Decision

Two HPAs:

1. **API HPA** (`k8s/hpa.yaml`): scales on CPU (primary) + HTTP requests/sec
   (secondary custom metric).  CPU is appropriate here because synchronous
   retrieval and reranking are CPU-bound.  Min=2 (zero-downtime rolling deploys),
   Max=10.

2. **Worker HPA** (`k8s/worker-hpa.yaml`): scales on `redis_list_length` for
   `judge:queue`.  Target AverageValue=50 items per worker replica — chosen so
   that at D4=19 s/job and concurrency=3, a single worker drains 50 items in
   ~317 s (within the 5-minute SLA).  Min=1, Max=8.

Redis queue depth is exposed to Prometheus via the `redis-exporter` deployment
(`k8s/redis-exporter.yaml`) and consumed by the HPA via `prometheus-adapter` or
KEDA.

## Alternatives Considered

- **Scale on CPU for workers** — ineffective; I/O-bound workers are idle from
  the scheduler's perspective.  Discarded.
- **KEDA ScaledObject** — cleaner than custom HPA + adapter; replaces this HPA
  entirely.  Preferred for production; deferred because KEDA is not yet installed
  on the cluster.
- **Fixed replica count** — simple but wastes money at low traffic and falls over
  at peaks.  Discarded.

## Consequences

- **Positive:** worker count tracks actual backlog; scales to zero workers minus
  one (Min=1) during quiet periods.
- **Negative:** requires Prometheus + redis-exporter + prometheus-adapter in the
  cluster (or KEDA); adds operational complexity.
- **Open question:** the 655-replica number at 1M/day suggests that at that scale,
  raising `JUDGE_WORKER_CONCURRENCY` (currently 3) to 10 would cut the worker
  count by 3.3× before any new infrastructure is needed.
