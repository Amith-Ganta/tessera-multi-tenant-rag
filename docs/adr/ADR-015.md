# ADR-015: Fail-Open Rate Limiter vs Fail-Closed Tenant Governor

**Status:** Accepted  
**Date:** 2026-09-23  
**Replaces:** n/a  
**Replaced by:** n/a

## Context

Tessera has two overlapping admission-control mechanisms:

1. **Rate limiter** (`src/resilience/rate_limiter.py`) — Redis fixed-window counter
   preventing request bursts per tenant.
2. **Tenant Governor** (`src/resilience/tenant_governance.py`) — Redis counters
   enforcing daily token budgets, concurrent request limits, and judge quotas.

Both depend on Redis. They have different failure semantics: the rate limiter is
fail-open; the tenant governor is fail-closed. This asymmetry is intentional and is
recorded here to prevent accidental "normalisation."

## Decision

The rate limiter (`RateLimiter.check`) catches Redis errors and returns 0 (fail-open).
When Redis is unavailable, rate limiting is silently disabled — requests proceed.

The tenant governor (`TenantGovernor`) catches all exceptions in every check method
and returns `False` (fail-closed). When Redis is unavailable, the governor rejects
the request with 429/503.

In environments without Redis (tests, local dev), a `NullTenantGovernor` passthrough
is substituted via `os.environ.get("REDIS_URL")` gate (`src/api/app.py:199–201`).

## Rationale

The two mechanisms have different risk profiles:

| Mechanism | If fail-open | If fail-closed |
|-----------|-------------|----------------|
| Rate limiter | Burst traffic allowed; recovers when Redis returns | Legitimate traffic blocked; service degraded |
| Tenant governor | Token/cost budgets may be exceeded; financial risk | Request rejected; user gets 503 |

Rate-limiting is a _best-effort_ admission boundary: momentary loss during a Redis
outage is acceptable because the outage is typically brief. Uncontrolled bursts during
a Redis outage do not threaten data integrity.

Token budgets and concurrent limits, by contrast, protect against unbounded cost
accumulation and resource starvation. Fail-open here could allow a single tenant to
exhaust the entire LLM budget during a Redis outage. Fail-closed is the safer default.

## Alternatives Considered

| Alternative | Rejected because |
|-------------|-----------------|
| Both fail-open | Unbounded cost accumulation during Redis outages |
| Both fail-closed | Rate-limit Redis failure would take down the API for all users |
| Circuit-breaker on Redis | Adds complexity; core asymmetry remains the same |

## Trade-offs

- Fail-closed governor causes false-positive 503s during Redis outages. The window is
  bounded by Redis availability SLA (typically < 60 s for a restart).
- Fail-open rate limiter allows brief bursts, which the LLM provider's own rate
  limits further constrain.

## Consequences

1. Tests must use `NullTenantGovernor` or mock `REDIS_URL` to avoid false failures.
2. Operators must monitor Redis availability — governor failures will produce 503s
   for all tenant-limited endpoints.
3. The audit report (`docs/AUDIT_REPORT_2026-09-24.md`) flags this asymmetry
   as DONE AND CORRECT.

## Operational Impact

When Redis is unavailable:
- `/ask` returns 503 ("tenant daily token budget exceeded") from the governor.
- Rate-limit counters are not incremented but requests proceed.

See runbook `redis-failure.md` for mitigation steps.

## Revisit Trigger

If the cost of false-positive 503s is deemed too high (e.g. Redis flaps frequently),
consider a short-TTL in-process budget cache that lets the governor fail-open with
a bounded over-spend window.
