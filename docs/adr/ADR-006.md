# ADR-006 — In-Process Async Judging Is a Stopgap, Not a Concurrency Model

**Status:** Superseded by [ADR-007](ADR-007.md)  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

Phase 4a moved judge evaluation off the request path.  Before that change, a
request that asked for evaluation paid for it inline; after it, `submit_judge`
dispatched the work with `asyncio.create_task()` and returned a `trace_id`
immediately.

The measured effect was large and, taken alone, looked like a finished piece of
work.  Four diagnostics were run against the live server:

| Diagnostic | Result |
|---|---|
| D1 — `submit_judge` return time | 0.030 ms (fire-and-forget confirmed) |
| D2 — peak concurrent judges | 6, unbounded |
| D3 — single async eval request | 3,991 ms |
| D4 — single sync eval request | 19,297 ms |

D3 against D4 is the win: 19,297 ms to 3,991 ms, because the request stops
waiting for the evaluation.  D2 is the problem hiding inside it.

Six concurrent judges arose under **20 sequential requests** — not under a load
test, not under a burst, but under the mildest possible traffic.  Nothing in
`asyncio.create_task()` bounds the number of tasks in flight; the ceiling is
whatever arrival rate the server happens to see.  Those judges compete with the
request path for the GIL, for the provider's concurrency quota, and for the HTTP
connection pool.  At 10× traffic the quota loss shows up as 429s on the request
path, which means a background quality feature degrades the foreground product.

There is a second defect with a different shape.  The tasks live only in the
API process's event loop, so a pod restart mid-evaluation loses them silently.
The caller already holds a `trace_id` that will now never resolve, and nothing
in the system reports that it will not.

## Decision

Record the in-process async path as a **known-insufficient stopgap** rather than
leave it as the implicit architecture, and remediate it with a bounded
out-of-process queue.

The concrete remediation is specified in [ADR-007](ADR-007.md): Redis
LPUSH/BRPOP with a separate worker process, `JUDGE_WORKER_CONCURRENCY = 3`, a
queue depth cap of 100, and HTTP 503 with `Retry-After: 60` on overflow.

This record exists separately from ADR-007 because the diagnosis and the fix are
separable, and the diagnosis is the more transferable half.  The lesson is not
"use a queue".  It is that moving work off the request path is not the same as
bounding it — the async dispatch solved the latency symptom completely while
leaving the resource contention entirely unaddressed, and D3 alone would have
been read as success.  D2 is the number that contradicted it, and D2 was only
collected because concurrency was measured separately from latency.

The in-process path is retained deliberately as a fallback: `JUDGE_QUEUE_ENABLED=False`,
or an unreachable Redis, falls back to it automatically, so a dev environment
without Redis continues to work.  It is an acceptable degradation, not an
acceptable production design.

## Alternatives Considered

- **Keep unbounded `asyncio.create_task()`** — no new infrastructure, and the
  latency win is already banked.  Discarded: D2 = 6 was visible at trivial load,
  so the failure mode is not hypothetical, and it worsens exactly when traffic
  is most valuable.
- **In-process `ThreadPoolExecutor` with a bounded pool** — genuinely bounds
  concurrency, and needs no new dependency.  Discarded: the bound is the only
  thing it fixes.  The work stays in the API process, so it still competes for
  the GIL and still dies with the pod, and the lost-job defect survives untouched.
- **A semaphore around the existing tasks** — the smallest possible change, and
  it caps in-flight judges.  Discarded for the same reason as the thread pool,
  with less benefit: bounded but still in-process, still lost on restart.
- **Reduce the number of evaluation metrics** — fewer provider calls per judge,
  so less contention per unit of traffic.  Discarded: it buys headroom by
  weakening the evaluation, which is the thing the feature exists to provide.

## Consequences

- **Positive:** the limitation is written down, so the async path is not mistaken
  for the intended design by anyone reading the code afterwards.
- **Positive:** the fallback behaviour is now a documented deliberate choice
  rather than an accident of the implementation order.
- **Negative:** whenever the fallback path is active — Redis down, or the queue
  disabled — every defect described here is live again, unbounded and
  restart-lossy.  The fallback preserves availability by reinstating the problem.
- **Open question:** post-fix D2 under live traffic has not been observed.  The
  queue path is bounded to 3 by worker configuration, so it is bounded by
  construction rather than by measurement.  The case study records this as an
  open item, and it remains open.
