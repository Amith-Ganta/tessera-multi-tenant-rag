# ADR-002 — Google A2A Protocol for Inter-Agent Communication

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

The answer path is a supervised loop between two agents: a Drafter that produces
an answer from retrieved context, and a Judge that scores it and returns feedback
the Drafter can act on.  The supervisor in `src/orchestrator/a2a_supervisor.py`
runs that loop.

The simplest implementation is a direct function call from the supervisor into
each agent.  It works, and it has no network cost.  What it does not give is a
boundary: the two agents share a process, a dependency set, and a deployment
lifecycle, so they cannot be scaled, restarted, or replaced independently, and
nothing external can drive either of them.  The Judge in particular is the part
most likely to want its own resources — it is the component the Redis queue
(ADR-007) later moves off the request path entirely.

If a boundary was going to exist, the question was whether to invent its wire
format or adopt one.

## Decision

Implement the Google Agent-to-Agent (A2A) specification directly, in
`src/agents/a2a_protocol.py`.  Each agent is a FastAPI app exposing the two wire
primitives the spec defines:

1. **AgentCard discovery** at `GET /.well-known/agent.json` — a JSON document
   naming the agent, its capabilities, and its skills.
2. **JSON-RPC 2.0** at `POST /`, accepting the `message/send` method and
   returning a completed task with artifacts.  Unknown methods return JSON-RPC
   error `-32601`; a handler exception returns `-32603`.  Both are HTTP 200 with
   an `error` object, as the JSON-RPC spec requires.

Structured skill parameters travel in `message.metadata`.  For clients that emit
only text parts, a JSON object in the first text part is parsed as an equivalent
fallback, so a simple client still interoperates.  Handlers run via
`run_in_threadpool`, so a slow generation does not block the agent's event loop.

The wire format is the spec itself rather than a vendored SDK.  An `a2a-sdk`
dependency is declared for teams who prefer the SDK client, but nothing in the
module imports it, so the agents run on the project's existing frozen dependency
set.

**Transport failure degrades rather than fails.**  `_call_drafter()` attempts the
HTTP path, and on any exception records a `fallback_events` increment, writes a
`drafter_fallback` entry into the run transcript, and re-executes the same skill
function in-process — timing the recovery separately so the cost is visible.  It
then sets `self.mode = "in_process"` for the remainder of that supervisor's life,
so a down agent is not re-attempted on every turn of the loop.

## Alternatives Considered

- **Direct in-process function calls** — no network hop, no serialisation, and
  the simplest possible code.  Discarded as the primary path: it provides no
  isolation and no independent deployability.  Note that it was not discarded
  entirely — it is retained as the fallback path and as the default for local
  runs, which is where its simplicity is actually worth having.
- **A custom JSON-over-HTTP RPC** — a few dozen lines, fully under our control.
  Discarded: the result would be a worse-specified version of A2A, with
  discovery, task/artifact shape, and error codes all invented rather than
  inherited, and no interoperability with anything.
- **gRPC** — mature, efficient, with generated clients.  Discarded: it adds a
  protobuf toolchain and a new dependency for a two-agent loop, and it is not the
  protocol the surrounding ecosystem speaks.
- **A shared message queue between agents** — durable and decoupled.  Discarded
  for the Drafter path, which is request-synchronous and needs a reply.  It was
  adopted for the Judge path, where the work is genuinely asynchronous
  (ADR-007) — the two decisions are complementary, not competing.

## Consequences

- **Positive:** the agents are independently deployable and independently
  scalable, and each is reachable by any standards-compliant A2A client, not only
  by this supervisor.
- **Positive:** discovery is self-describing, so an agent's capabilities are read
  from the running agent rather than from documentation that can drift.
- **Positive:** the fallback means an unreachable agent costs latency and a
  transcript entry, not a failed request.
- **Negative:** one network hop and a JSON serialisation round-trip per agent
  call, on a path that also spends seconds in the model.  The hop is small
  relative to generation, but it is not free.
- **Negative:** the in-process fallback is sticky for the supervisor's lifetime.
  A brief transport blip therefore demotes that supervisor for the rest of the
  run, and it recovers only on the next instantiation.  There is no half-open
  retry as there is for the LLM circuit breaker (ADR-008).
- **Negative:** running the agents as separate services means more processes to
  operate, and it makes agent state a real concern — which is what ADR-009
  (Redis checkpointer) exists to resolve.
