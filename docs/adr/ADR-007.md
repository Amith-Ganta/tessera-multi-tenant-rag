# ADR-007 — Redis Message Queue for Judge Evaluation Jobs

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

Phase 4a measured D2 = 6 concurrent judge tasks in-flight at peak (10× traffic,
10K req/day).  The FastAPI process spawned those as unbounded asyncio tasks via
`asyncio.create_task()`.  Any burst beyond a few tasks simultaneously exhausted
the OpenAI concurrency quota and produced 429 rate-limit errors.  Additionally,
tasks were lost on pod restart — if the API process died mid-evaluation, the
caller received a `trace_id` that would never resolve.

## Decision

Replace `asyncio.create_task()` with Redis LPUSH/BRPOP.  The API process
publishes a serialised job envelope to `judge:queue` and returns immediately.
A separate `judge_worker.py` process drains the queue with a bounded pool of
`JUDGE_WORKER_CONCURRENCY=3` workers.  The queue cap (`JUDGE_QUEUE_MAX_DEPTH=100`)
causes the API to return HTTP 503 with `Retry-After: 60` when backpressure is
needed.  Results are stored in Redis under `judge:result:<trace_id>` with a
24-hour TTL.

## Alternatives Considered

- **Keep asyncio.create_task** — simple but unbounded; D2=6 already visible at
  10× load.  Discarded.
- **Celery** — full-featured task queue but adds a broker + worker process +
  `celery` as a new dependency.  Discarded (constraint: no new dependencies beyond
  `redis`).
- **SQS/Pub-Sub** — cloud-managed queue with durability, but tightly couples the
  project to a specific cloud.  Deferred to a future ADR.

## Consequences

- **Positive:** bounded concurrency; 503 instead of silent drop under overload;
  jobs survive API pod restarts (queue is durable until `JUDGE_QUEUE_MAX_DEPTH`).
- **Negative:** requires Redis in the runtime environment; adds a separate worker
  process to operate.
- **Mitigated:** `JUDGE_QUEUE_ENABLED=False` or Redis-unreachable falls back to
  the Phase 4a in-process path automatically, so dev environments without Redis
  continue to work.
