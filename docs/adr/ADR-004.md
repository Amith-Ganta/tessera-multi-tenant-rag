# ADR-004 — Per-Tenant Vectorstore Caching with Double-Checked Locking

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

Phase 1 per-stage instrumentation reported `vector_retrieval` at 3,696 ms p50
and 6,125 ms p95 against a local Chroma index over a small corpus — roughly 7 to
18 times what a local vector lookup should cost.

The instrumentation is what made this visible.  End-to-end latency was about
10 seconds, which is indistinguishable from an ordinary slow LLM call, and the
LLM was the assumed suspect.  Without a timer on each stage separately, this
would have been diagnosed as normal generation latency and left alone.

The diagnosis found two compounding defects, neither in the retrieval algorithm:

1. `get_vectorstore()` reconstructed the `OpenAIEmbeddings` client and the
   `Chroma` handle on **every call**, so per-process setup cost was being paid
   per request.
2. On the adaptive path it was called **twice per request** — once by
   `retrieve_hybrid()`, and again by `_top1_similarity()`, which needed the
   top-1 score for the re-ranking gate (ADR-003) and obtained it by issuing a
   second vector query.  Both the construction and the embedding round-trip were
   therefore doubled, inside a single timer.

The second defect is the more instructive one: a second network round-trip was
being spent to recover a number the first retrieval had already computed and
discarded.

## Decision

Two changes, in `src/rag/retriever_dense.py` and `src/rag/retriever_hybrid.py`.

**Cache the vectorstore, keyed by the resolved tenant index directory.**
Construction happens once per process per tenant index, not once per call:

```python
key = str(active_index_dir())
cached = _VECTORSTORE_CACHE.get(key)
if cached is not None:
    return cached
with _VECTORSTORE_LOCK:
    # Re-check inside the lock: another thread may have built it while we waited.
    cached = _VECTORSTORE_CACHE.get(key)
    if cached is not None:
        return cached
    vectorstore = _build_vectorstore()
    _VECTORSTORE_CACHE[key] = vectorstore
```

The key is the **resolved index directory**, never a process-global slot, so a
cache hit cannot hand one tenant another tenant's store.  This preserves the
isolation property that per-tenant Chroma directories exist to provide.

Double-checked locking keeps the common path lock-free — the first read happens
outside the lock — while guaranteeing exactly one construction under a race.
With four uvicorn workers and a thread pool per worker, that race is real, not
theoretical.

**Return dense scores from the first retrieval pass.**
`retrieve_hybrid(..., return_scores=True)` surfaces the dense cosine scores it
already computed, so `_top1_similarity()` became an in-memory read of the first
returned tuple instead of a second vector query.  Documents appearing only in
the sparse (BM25) arm have no dense score and are reported as `0.0` rather than
omitted; malformed input yields `SIMILARITY_UNKNOWN`, which ADR-003 routes to
running the re-ranker.

## Alternatives Considered

- **Process-global singleton vectorstore** — simplest possible cache, and the
  obvious first idea.  Discarded outright: with one slot, the second tenant to
  call would be served the first tenant's store.  That converts a latency bug
  into a cross-tenant data leak, which is a strictly worse failure.
- **Per-request cache** — thread-local or request-scoped memoisation would
  deduplicate the two calls within one request but still reconstruct the clients
  on every request.  Discarded: it fixes the smaller half of the problem and
  leaves the larger one.
- **Plain `functools.lru_cache` on `get_vectorstore()`** — concise, and correct
  on the key.  Discarded: its locking behaviour under concurrent misses is not
  something the code states explicitly, and the construction being guarded is
  expensive enough that the guarantee should be visible in the source rather
  than inherited from a decorator.
- **Keep the second vector query and just cache the client** — would have
  captured most of the win.  Discarded: the second query remained a real
  embedding round-trip, and the score needed was already in hand.

## Consequences

- **Positive:** `vector_retrieval` p50 dropped from 3,696 ms to 4 ms, roughly
  900×.
- **Positive:** client round-trip mean dropped from 10,318 ms to 6,044 ms.
- **Positive:** the re-ranking gate (ADR-003) now reads its confidence signal
  for free, so the two decisions reinforce rather than tax each other.
- **Negative:** cached entries accumulate per tenant index and are never
  evicted.  Memory grows with the number of distinct tenants a process has
  served, and there is no LRU bound or TTL.  At the current tenant count this is
  irrelevant; at a large tenant count it is a leak, and it is the first thing to
  revisit before this design scales.
- **Negative:** a cached `Chroma` handle outlives re-ingestion of that tenant's
  index.  The semantic cache handles staleness by carrying the index mtime; the
  vectorstore cache does not, so a process holding a handle across a re-index
  needs a restart or an explicit invalidation hook, which is not implemented.
- **Note:** the fix was not an algorithmic improvement.  The strongest single
  latency win in the project came from measuring per stage and finding an
  impossible number, which is the transferable lesson rather than the cache
  itself.
