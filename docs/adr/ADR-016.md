# ADR-016: Per-Tenant Resource Governance via Redis Counters

**Status:** Accepted  
**Date:** 2026-09-23

---

## Context

Tessera serves multiple tenants from a shared API process. Without per-tenant
resource limits a single tenant can exhaust the entire token budget, monopolise
all concurrent request slots, or flood the judge queue — all at the expense of
other tenants.  The existing `RateLimiter` (Phase 5) controls *per-minute
request counts* but does not bound *daily token spend*, *in-flight concurrency*,
or *judge evaluation calls*.

Three distinct resource axes need governance:

1. **Daily token budget** — LLM calls are priced by token.  A tenant generating
   millions of tokens per day can drive up cloud costs for the whole service.
2. **Concurrent request limit** — each in-flight `/ask` call holds a bulkhead
   slot; unbounded concurrency starves other tenants.
3. **Daily judge quota** — judge calls invoke a second LLM; unlimited evaluation
   requests multiply cost without proportional benefit.

---

## Decision

Introduce `TenantGovernor` (`src/resilience/tenant_governance.py`), a
Redis-backed fail-**closed** governor with three counters per tenant:

| Counter | Redis key pattern | TTL |
|---|---|---|
| Daily token usage | `tokens:<tenant>:<YYYYMMDD>` | 2 days |
| In-flight requests | `concurrent:<tenant>` | No TTL (live counter) |
| Daily judge calls | `judge_quota:<tenant>:<YYYYMMDD>` | 2 days |

**Fail-closed** means any Redis error (connection refused, timeout, WRONGTYPE)
causes the governor to deny the request.  This is the opposite of the existing
`RateLimiter`, which is fail-open (it passes requests when Redis is unavailable).
The difference is intentional: rate limiting is an admission boundary (it is
acceptable to let a burst through when Redis is briefly unavailable), whereas
tenant governance is a fairness boundary (allowing unlimited tokens or
concurrency during Redis downtime would defeat the purpose entirely).

Wiring in `/ask`:

* **Token check** — immediately after the per-minute rate limiter; 429 if
  exceeded.  Token estimate = `len(question) // 4` (worst-case pre-LLM
  estimate; actual usage is not tracked post-hoc in this iteration).
* **Concurrent acquire** — after parameter validation and A2A early-exit, before
  strategy execution; 503 if limit reached.  Released unconditionally on normal
  return and on every exception path.
* **Judge quota** — before `submit_judge`; if exceeded the eval field is set to
  `{"status": "quota_exceeded", "reason": "tenant_judge_quota"}` and the judge
  call is skipped entirely.

Default limits (overridable via environment variables):

| Constant | Default | Env var |
|---|---|---|
| `TENANT_DAILY_TOKEN_BUDGET` | 2 000 000 | `TENANT_DAILY_TOKEN_BUDGET` |
| `TENANT_MAX_CONCURRENT` | 5 | `TENANT_MAX_CONCURRENT` |
| `TENANT_DAILY_JUDGE_QUOTA` | 200 | `TENANT_DAILY_JUDGE_QUOTA` |

---

## Alternatives Considered

**Fail-open (like the rate limiter)** — Rejected.  Redis downtime would
temporarily suspend all fairness guarantees, allowing a single tenant to consume
unbounded tokens.

**In-process counters** — Rejected.  They do not survive process restarts and
provide no isolation across API replicas.  Redis shared state is required for
multi-replica deployments.

**Middleware layer instead of explicit checks** — Considered.  A FastAPI
middleware would intercept all routes, but governance only applies to `/ask`;
explicit checks inside the handler make the intent visible and allow the token
estimate to be computed from the actual question length.

---

## Consequences

* Per-tenant fairness is now enforced across all three resource axes.
* Redis is now a hard dependency for `/ask`: Redis failure causes the request to
  be denied rather than passed through.  This aligns with the design intent but
  operators must ensure Redis HA before enabling governance in production.
* The token estimate (`len(question) // 4`) is conservative.  The actual LLM
  token count is higher (system prompt, context chunks, completion).  A future
  iteration should record actual token usage from the LiteLLM response and
  deduct it from the budget post-call, replacing the pre-call estimate.
