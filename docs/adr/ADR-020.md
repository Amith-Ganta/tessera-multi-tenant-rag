# ADR-020: Structured RAG Quality Signals as a Separate Observability Record Type

**Status:** Accepted  
**Date:** 2026-09-24

---

## Context

The `logs/analytics.jsonl` file already captures one record per `/ask` call (type
`ask`), containing tenant, strategy, model, latency, token count, and answer.
Phase B4 introduced richer quality signals: retrieval scores, reranker scores,
eval pass-rate, guard retries, and estimated cost.

Two design options were considered for where to attach this data.

---

## Decision

Emit a **separate record** with `"type": "rag_quality"` via a dedicated
`record_rag_signals()` function in `src/observability/rag_signals.py`.
This record is written to the same `logs/analytics.jsonl` file as the existing
`ask` records and is linked to the same request by tenant and strategy, but is
structurally independent.

---

## Alternatives Considered

### 1. Enrich the existing `ask` record (rejected)

Add quality signal fields directly to the dict that `log_analytics()` receives in
`src/api/app.py`.

**Rejected because:**
- The `ask` record is assembled deep in `app.py` where raw retrieval scores are not
  available without threading them through multiple function arguments.
- Adding optional fields to the record increases the `ask` schema surface area and
  makes the record harder to query — many downstream queries only need one subset.
- The `ask` record is assembled before async judge completion; quality signals
  (especially eval metrics) arrive later.

### 2. Separate log file (rejected)

Write quality signals to `logs/rag_quality.jsonl`.

**Rejected because:**
- Splits observability across two files, complicating log aggregation and retention.
- The analytics pipeline already reads `logs/analytics.jsonl`; adding a second file
  requires changes to all downstream readers.

### 3. In-band in AskResponse (rejected)

Return quality signals as part of the API response body.

**Rejected because:**
- Increases response payload size for every request even when the caller doesn't use it.
- Eval metrics are async — they are not available at response time on the async path.

---

## Consequences

**Positive:**
- Quality signals are optional and additive: callers that don't call
  `record_rag_signals()` produce no record.
- The function is fully fail-safe (any exception returns `{}`), so the `/ask` path
  is never degraded by a quality-signal failure.
- Separate records make filtering easy: `jq 'select(.type=="rag_quality")'`.
- The `ask` record schema is unchanged — no AskResponse impact.

**Negative / trade-offs:**
- Linking a `rag_quality` record to its originating `ask` record requires joining on
  tenant + timestamp; there is no explicit `trace_id` field in the quality record.
- An operator monitoring both record types must handle the case where one arrives
  without the other (e.g., if `record_rag_signals()` is skipped or fails).
