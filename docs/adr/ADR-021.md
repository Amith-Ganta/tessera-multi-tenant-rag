# ADR-021: At-Most-Once Judge Queue Delivery

**Status:** Accepted  
**Date:** 2026-09-24

---

## Context

The judge queue (`src/judge/queue.py`) uses Redis LIST semantics. When a worker
calls `get_job()`, the job is `BLPOP`-ed from the queue and immediately owned by
that worker. If the worker crashes before writing the eval result, the job is lost.

Two delivery guarantees were considered:

- **At-most-once**: pop on dequeue; if the worker crashes, the job is lost.
- **At-least-once**: use `RPOPLPUSH` to move the job into a processing list;
  re-queue after a TTL if no acknowledgment is received.

A failed publish to the main queue causes the job to go to the DLQ
(`src/judge/queue.py::publish()`). However, the DLQ push itself is also
at-most-once: if Redis is unavailable during the DLQ push, the job is silently
dropped.

---

## Decision

Retain **at-most-once delivery** for the current phase.

Jobs that fail during execution push to the DLQ. The DLQ is drained manually
via `DELETE /admin/dlq` or automatically as the worker retries.
The DLQ push is best-effort; Redis unavailability causes silent drop, not an
exception propagated to the `/ask` caller.

---

## Alternatives Considered

### 1. At-least-once via RPOPLPUSH + visibility timeout (deferred, not rejected)

Use `RPOPLPUSH queue processing-list` on dequeue. A separate reaper process
re-queues jobs whose processing-list entry is older than a TTL.

**Not implemented now because:**
- Requires a reaper process (additional operational surface).
- Eval results populate the `eval` field of a future `/ask` request; a duplicate
  eval is idempotent as the newer result overwrites the older.
- The primary use case for evals is quality monitoring, not billing — a missed
  eval is observable but not catastrophic.
- At-least-once semantics would be the right upgrade when eval becomes mandatory
  for access control or billing decisions.

### 2. Persistent job store (e.g., SQLite or Postgres)

Store all pending eval jobs in a durable table; mark as complete on success.

**Not implemented now because:**
- Introduces a synchronous write on every `/ask` call, increasing p50 latency.
- Adds a new persistence dependency on a code path that is already optional/async.
- SQLite is already used for A2A checkpointing; mixing eval jobs there conflates
  two different concerns.

---

## Consequences

**Positive:**
- Simple implementation — no reaper, no processing-list, no TTL management.
- Fail-closed DLQ (`peek_dlq` / `drain_dlq`) gives operators visibility into
  recent failures, even if the root delivery guarantee is at-most-once.
- At-most-once is appropriate for quality-signal evals that do not gate access.

**Negative / trade-offs:**
- A worker crash loses the eval for that request.
- Redis unavailability during DLQ push causes silent drop (no exception to caller).
- If eval results are ever required for billing or SLA enforcement, this ADR must
  be revisited and at-least-once semantics implemented before that migration.

---

## Upgrade path

When at-least-once becomes required:
1. Replace `BLPOP` in `get_job()` with `RPOPLPUSH queue processing-list`.
2. Add a reaper task (`asyncio.create_task`) that scans `processing-list` for
   stale entries and re-queues them.
3. Add worker `ACK` call to remove the job from `processing-list` on success.
4. Document in a new ADR that supersedes this one.
