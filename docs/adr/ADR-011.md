# ADR-011: Canary deployment for model version changes

**Status:** Accepted
**Date:** 2026-09-19
**Deciders:** Amith Ganta

## Context

Tessera can swap chat and judge models via config. A bad model version
would affect all tenants simultaneously without a phased rollout. The
existing eval gate blocks regressions on a golden set but does not catch
distribution shift on live traffic.

## Decision

Introduce `MODEL_CANARY_PERCENT` (0-100). Requests are hashed by
`tenant_id`; if `hash % 100 < MODEL_CANARY_PERCENT`, the request uses
the canary model version. Eval scores for both versions are logged to
Langfuse with a version tag. Promotion to 100% only after the new
version matches or beats the old on faithfulness and answer relevancy
over at least 1,000 requests.

The hash function is SHA-256 truncated to an integer modulo 100, giving
a deterministic, stable assignment per tenant that does not change across
restarts or replicas.

## Alternatives Considered

- **Blue-green deployment** — swaps 100% of traffic at once. Rejected:
  needs duplicate capacity and offers no gradual signal.
- **Shadow mode** — runs both models on every request, discards canary
  response. Rejected: does not test real user behaviour; doubles cost.
- **Feature flags per tenant** — explicit opt-in list. Deferred: useful
  for enterprise tiers but adds API surface. The hash approach is
  automatic and requires no per-tenant configuration.

## Consequences

- **Gain:** bad model versions affect at most `MODEL_CANARY_PERCENT`%
  of traffic during rollout.
- **Gain:** A/B comparison of eval scores per version via Langfuse tags.
- **Pay:** running two model integrations in parallel during rollout.
- **Pay:** rollback requires flipping `MODEL_CANARY_PERCENT` to 0, not
  redeploying (faster but requires a config reload).
- **Invariant:** the 14-field `AskResponse` shape is unchanged; the
  canary decision is an internal routing detail only.
