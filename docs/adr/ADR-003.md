# ADR-003 — Conditional Cross-Encoder Re-ranking at a 0.90 Similarity Threshold

**Status:** Accepted  
**Date:** 2026-09-17  
**Deciders:** Amith Ganta  

## Context

The cross-encoder re-ranker (`cross-encoder/ms-marco-MiniLM-L-6-v2`, in
`src/rag/reranker.py`) scores every query-document pair with a full transformer
forward pass.  Unlike the bi-encoder used for dense retrieval, nothing can be
precomputed: the cost is paid per request, over the whole candidate set, and it
scales with `RETRIEVER_TOP_K`.

The re-ranker earns that cost only when the retrieval ordering is genuinely
ambiguous.  When hybrid retrieval already returns a clearly correct top-1
document, reordering a list whose first element is right cannot improve the
answer — it can only delay it.  Running the stage unconditionally charges every
request for a correction that most requests do not need.

## Decision

Gate the re-ranker on retrieval confidence, using the top-1 dense cosine
similarity already computed by `retrieve_hybrid(..., return_scores=True)`
(see ADR-004 — this number is read from the existing result, not re-queried).

`_maybe_rerank()` in `src/rag/strategies.py` applies three rules:

1. **Empty retrieval** — skip.  There is nothing to reorder, and calling the
   model on an empty candidate set is a crash risk with no upside.
2. **top-1 similarity strictly greater than `RERANK_SKIP_THRESHOLD` (0.90)** —
   skip.  Retrieval is confident.
3. **Anything else — including exactly 0.90, and including
   `SIMILARITY_UNKNOWN`** — run the re-ranker.

The asymmetry at the boundary is deliberate.  The skip requires a strict
inequality, so ties and unknowns fall through to running the stage.  A needless
re-rank costs latency; a wrongly skipped one costs a wrong answer.  The
scoring path is built so that any malformed or missing score degrades into
*doing more work*, never into silently skipping a quality step.

Every decision is written to the structured trace with its reason, so the skip
rate is auditable rather than assumed.

## Alternatives Considered

- **Run the re-ranker unconditionally** — simplest, and strictly the best
  ordering quality.  Discarded: it charges a per-request transformer pass on the
  majority of queries where the top-1 was already correct.
- **Skip at 0.85** — a lower bar skips more often and saves more.  Discarded as
  too aggressive: 0.85 is inside the band where dense retrieval is plausibly
  wrong about ordering, which is exactly the band the re-ranker exists to fix.
- **Skip at 0.95** — safer, but rarely triggers.  Discarded: a gate that almost
  never fires is equivalent to no gate, with added branch complexity.
- **Always re-rank, but on fewer candidates** — caps the cost instead of
  eliminating it.  Discarded for now: it degrades recall on the ambiguous
  queries that need the re-ranker most, which is the wrong direction to trade.

## Consequences

- **Positive:** on the confident path the stage is a float comparison rather
  than a model call.  Measured `reranking` p50 is 0.004 ms across 20 samples in
  the Phase 2 and Phase 3 latency runs, all of which took the skip branch.
- **Positive:** the fallback direction is safe by construction — unknown or
  malformed scores run the re-ranker.
- **Negative:** a query whose top-1 similarity exceeds 0.90 but whose top-1
  document is wrong will not be corrected.  The gate trusts the bi-encoder in
  precisely the region where the bi-encoder is most likely to be right, but
  "most likely" is not "always".
- **Negative:** 0.90 is a judgement call, not a tuned value.  It was not derived
  from a sweep against labelled ambiguity, and it is cosine-similarity-scale
  dependent — changing `EMBEDDING_MODEL` would invalidate it.
- **Unmeasured:** the repo has no measurement of the re-ranker's cost when it
  actually runs.  Every recorded `reranking` sample is a skip, so the saving is
  reasoned rather than measured, and the skip rate under mixed production
  traffic is unknown.  Capturing both requires a workload containing
  low-confidence queries, which the current golden set does not supply.
